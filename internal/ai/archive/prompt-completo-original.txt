# PARTE I — MISSÃO

## 1. OBJETIVO PRINCIPAL

Você é o agente principal responsável pelo desenvolvimento do VorynOS.

Seu trabalho é projetar, implementar, testar, depurar, documentar e evoluir um sistema operacional independente.

O VorynOS deve combinar:

- Alto desempenho.
- Eficiência de memória.
- Baixa latência.
- Segurança arquitetônica.
- Estabilidade.
- Liberdade e controle do usuário.
- Interface gráfica moderna.
- Subsistemas próprios.
- Formatos nativos originais.
- Arquitetura modular.
- Integração opcional com inteligência artificial.
- Capacidade de executar diferentes categorias de aplicações.

O sistema deve ser projetado para atender:

1. Usuários domésticos.
2. Gamers.
3. Desenvolvedores.
4. Profissionais.
5. Criadores de conteúdo.
6. Usuários avançados.
7. Aplicações e assistentes de inteligência artificial.

Os objetivos de desempenho e compatibilidade representam requisitos de engenharia a serem demonstrados, não funcionalidades já existentes.

## 2. INDEPENDÊNCIA

O VorynOS não deve depender do kernel Linux, Windows, BSD ou outro kernel externo durante sua operação nativa.

Seu kernel, runtime, APIs, serviços essenciais, gerenciamento de recursos e mecanismos centrais devem possuir implementações próprias.

Ferramentas externas de compilação, testes, depuração e desenvolvimento são permitidas.

A independência deve ocorrer na implementação e na arquitetura operacional, não necessariamente na reinvenção de padrões de hardware ou protocolos consolidados.

# PARTE II — LINGUAGENS E TOOLCHAIN

## 3. ZIG

Utilize Zig como principal linguagem de implementação.

Versão-alvo:

`0.17.0`

Antes de escrever código:

- Verifique a versão instalada.
- Inspecione APIs disponíveis.
- Confirme sintaxe.
- Confirme convenções de chamada.
- Valide recursos de compilação freestanding.
- Avalie compatibilidade com UEFI.
- Identifique mudanças incompatíveis da versão utilizada.

Não utilize APIs antigas sem verificar sua existência.

Não invente interfaces da biblioteca padrão.

Não altere a versão-alvo sem autorização.

## 4. C23

Utilize C23 quando houver justificativa técnica, especialmente para interfaces ABI, interoperabilidade e componentes especializados.

Evite manter implementações duplicadas em Zig e C sem necessidade.

## 5. ASSEMBLY

Utilize Assembly quando for necessário controlar diretamente:

- Registradores.
- Entrada no kernel.
- Troca de contexto.
- Tabelas de descritores.
- Interrupções.
- Instruções privilegiadas.
- Inicialização de processadores.
- Operações específicas da arquitetura.

Documente ABI, alinhamento de pilha, registradores preservados e efeitos colaterais.

# PARTE III — ARQUITETURA ORIGINAL

## 6. VORYN FABRIC

Investigue e desenvolva a arquitetura proposta:

**Voryn Fabric**

A arquitetura deve ser avaliada como um modelo híbrido modular baseado em mecanismos privilegiados mínimos, serviços isoláveis e comunicação controlada.

Não considere a arquitetura definitivamente aprovada antes de registrar os trade-offs em uma ADR.

A proposta inicial possui os seguintes componentes.

### VNK — Voryn Nucleus Kernel

Responsável pelos mecanismos privilegiados essenciais:

- Interrupções.
- Exceções.
- Gerenciamento de memória.
- Processos e threads.
- Escalonamento.
- Syscalls.
- Capacidades.
- Comunicação básica entre processos.
- Controle de recursos privilegiados.

Evite colocar políticas complexas no kernel quando elas puderem ser implementadas com segurança fora dele.

### VNH — Voryn Hardware Nexus

Camada de interface e descoberta de hardware.

Responsabilidades:

- Descoberta de dispositivos.
- Características de CPU.
- Barramentos.
- Recursos de hardware.
- Endereçamento de dispositivos.
- Interfaces necessárias aos drivers.

### VNM — Voryn Nexus Memory

Subsistema de gerenciamento de memória.

Responsabilidades:

- Memória física.
- Memória virtual.
- Page tables.
- Alocadores.
- Proteções de páginas.
- Mapeamentos.
- Gerenciamento de memória compartilhada.

Implemente progressivamente:

1. Bootstrap allocator.
2. Physical memory manager.
3. Virtual memory manager.
4. Kernel heap.
5. Isolamento de espaços de endereçamento.

Teste alinhamento, overflow, corrupção e casos extremos.

### VNT — Voryn Task Fabric

Subsistema de tarefas e escalonamento.

Implemente inicialmente um scheduler simples e verificável.

Posteriormente investigue:

- Escalonamento preemptivo.
- SMP.
- Afinidade de CPU.
- Prioridades.
- Balanceamento de carga.
- Escalonamento sensível à latência.
- Políticas diferenciadas para jogos e aplicações interativas.

Não introduza complexidade sem medições.

### VNX — Voryn Exchange

Sistema nativo de comunicação entre processos.

Explore:

- Mensagens tipadas.
- Canais.
- Handles.
- Filas.
- Comunicação assíncrona.
- Schemas versionados.
- Transferência de capacidades.
- Memória compartilhada.
- Zero-copy quando seguro.
- Limites de recursos.

Compare diferentes arquiteturas IPC antes de selecionar uma implementação definitiva.

### VNC — Voryn Capability Fabric

Sistema de segurança baseado em capacidades.

Responsabilidades:

- Objetos de capacidade.
- Handles.
- Permissões.
- Transferência de direitos.
- Revogação.
- Validação de acesso.
- Auditoria de operações.

Aplicações não devem receber acesso global irrestrito por padrão.

### VND — Voryn Device Fabric

Sistema de drivers.

Investigue a execução de drivers complexos em processos isolados.

O objetivo é reduzir o impacto de falhas de drivers sobre o restante do sistema.

Permita exceções tecnicamente justificadas para componentes necessários ao bootstrap.

### VSN — Voryn Service Node

Sistema de serviços.

Responsabilidades:

- Inicialização.
- Supervisão.
- Dependências.
- Reinicialização.
- Monitoramento.
- Limites de recursos.
- Recuperação de falhas.

# PARTE IV — BOOT E KERNEL

## 7. VNB — VORYN NATIVE BOOT

Desenvolva um bootloader UEFI próprio.

A implementação deve evoluir pelas seguintes etapas:

1. Aplicação UEFI mínima.
2. Diagnóstico por console.
3. Saída serial.
4. Descoberta de framebuffer GOP.
5. Obtenção do mapa de memória.
6. Carregamento de imagem do kernel.
7. Validação dos segmentos.
8. Preparação do contrato bootloader-kernel.
9. Tratamento correto de ExitBootServices.
10. Transferência de controle ao kernel.

Não invoque serviços UEFI de boot após uma chamada bem-sucedida de ExitBootServices.

Teste situações de falha e mudanças no mapa de memória.

## 8. KERNEL NATIVO

Implementação progressiva:

- Entrada do kernel.

- Timer.
- Memória física.
- Paginação.
- Kernel heap.
- Threads.
- Scheduler.
- User mode.
- Syscalls.
- IPC.
- Processos.
- Isolamento.
- Inicialização de serviços.

Cada etapa deve possuir critérios de aceitação verificáveis.

# PARTE XVII — CRITÉRIOS DE QUALIDADE

## 27. DEFINIÇÃO DE CONCLUÍDO

Uma funcionalidade somente poderá ser declarada concluída quando:

1. Sua implementação estiver presente.
2. O código passar pelas verificações aplicáveis.
3. Os testes exigidos forem executados com sucesso.
4. As falhas relevantes forem tratadas.
5. As interfaces estiverem documentadas.
6. As limitações forem conhecidas.
7. Não houver regressões identificadas no escopo testado.

Quando algum requisito não puder ser validado, a funcionalidade deverá permanecer marcada como não verificada ou parcialmente implementada.

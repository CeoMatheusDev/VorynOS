## 1. Version identification

This release consolidates, in a single public milestone, all the technical
progress the project has already verified. It is **not** a restart: the code,
the history and the earlier decisions remain, and the milestone only gathers
them into a coherent and verifiable state.

The previous version with the same identifier was removed and recreated over
the final validated commit. The procedure, with the record of the original

## 2. Overview

The **VorynOS** is an independent operating system, written from scratch. The
kernel is written in **Zig 0.17.0**, with **x86_64 Assembly** at the points
where the architecture requires direct control of the processor: the entry
point of the processor, the context switch, the interrupt table, the task
state segment, the system call and the entry of the call.

The **independence of the VorynOS is architectural, and not a matter of
tooling**: the product — the bootloader, the kernel and the tools — does not
depend on any host operating system at run time, and the kernel is loaded and
executed directly on top of the UEFI firmware.

**The build and the validation, however, use tools that run on host
systems**: the Zig compiler, QEMU and the OVMF firmware are development
tools, and the reference environment of this version is Fedora Linux 44. The
distinction matters: the independence of the product is not the absence of
development dependencies.

The goal of this version is to give the project **one public and coherent
baseline**, from which the version numbering makes sense again.

## 3. Architecture

```text
   UEFI Firmware (OVMF)
             │
             │  ExitBootServices
             ▼
   ┌──────────────────────┐
   │  VNB — Voryn Native  │  UEFI application in Zig, without libc
   │        Boot          │  1. serial console + firmware console
   └──────────┬───────────┘  2. framebuffer (GOP)
              │               3. memory map
              ▼               4. reading and validation of the ELF64 image
   ┌──────────────────────┐  5. relative relocations
   │  VNK — Voryn Nucleus │  6. handoff contract
   │        Kernel        │  7. jump to the kernel
   └──────────┬───────────┘
              │  Ring 0: GDT, TSS, IDT, memory, heap, timer,
              ▼            preemptive scheduler, processor frame
   ┌──────────────────────┐
   │  Ring 3: processes   │  `syscall` instruction, eight calls,
   │  with their own      │  VNX channels, a wait that does not
   └──────────────────────┘  occupy the processor
```

The boundary between the bootloader and the kernel is the versioned handoff
contract, with validation of the *magic*, of the version and of the coherence
of the memory map. The boundary between the user mode and the kernel is the
system call contract, at version `syscall_abi = 3`.

## 4. Implemented components

### 4.1 VNB — bootloader (`boot/uefi/`)

- Initialization as a UEFI application, with the services of the firmware.
- Dual console: the firmware console and the COM1 serial port at 115200 baud.
- Discovery of the framebuffer through the GOP, with the selection of a
  32 bits per pixel mode.
- Reading and normalization of the memory map of the firmware.
- Reading of the kernel image in the EFI volume, with validation of the
  ELF64 structure, of the segments and of the relocations.
- Application of `R_X86_64_RELATIVE` relocations only.
- Preparation of the handoff contract and termination of the boot services
  with `ExitBootServices`, with a new attempt when the memory map changes.
- Controlled transfer of the execution to the kernel.

### 4.2 VNK — kernel (`kernel/`)

- Own entry point in x86_64, with a boot stack and declared ABI rules.
- Global segment table, with the segments of level 0 and of level 3, and the
  task state segment of the 64 bit mode with the layout verified at compile
  time.
- Interrupt table with 256 entries, and exception handling with the report
  of the vector, of the error code, of the address that caused the fault and
  of the processor frame.
- Physical memory manager over a bitmap, with a coverage of 4 GiB.
- Own page tables, with the identity mapping of the kernel image and of the
  framebuffer, and the switch of `CR3`.
- Kernel heap with boundary tags, block merging and corruption detection.
- 8254 timer at 100 Hz, with the 8259 controllers reprogrammed.
- Circular preemptive scheduler, without starvation, with the measurement of
  the cost of the switch by the time counter of the processor.
- Task context with **all** the registers of the processor, and kernel stack
  separated from the code stack.

### 4.3 User mode, processes and communication

- Execution in the third privilege level, with the `syscall` instruction as
  the entry door and `iretq` on the way back.
- User mode window with no fixed address, chosen outside the kernel image
  and delivered to the task at the moment of its creation.
- Own address space per process, with the tables of the kernel copied into
  it, and the switch of the space together with the switch of the context.
- **Eight** system calls: `ping`, `write`, `memcpy`, `exit`, `send`,
  `receive`, `copy_to` and `receive_blocking`.
- VNX message channels, with one queue per side, and the delivery of a
  message from one process to another.
- Copy of a block of memory from one process to the other, with the reading
  of the source and the writing of the destination done in the space of each
  one.
- A wait that **does not occupy the processor**: the task that waits is
  marked as blocked, the scheduler chooses another one, and the message
  wakes it up with the result already in the saved context.

### 4.4 Build tools (`tools/`, `scripts/`)

- Builder of a FAT16 boot image, with the bootloader and the kernel.
- Source packaging script, with a reproducible archive and a SHA-256
  summary, and an explicit refusal when the package carries internal files.

## 6. Important corrections

1. **The context switch lost the registers that the architecture does not
   preserve between calls.** The result of a system call was lost on every
   switch, and the task of the user mode wrote values that belonged to
   another task. The context now saves the fifteen registers.
2. **The processor frame of the way back was built over the stack of the
   interrupted code.** For the user mode, the frame was in a page that the
   user owns, and the privilege level of the way back became controlled by
   the user. The frame is now built in the kernel stack of the task.
3. **The user mode window had a fixed address inside the kernel image**,
   which is identity mapped and grows. The page of the process erased the
   data segment of the kernel itself. The window is now chosen outside the
   image.
4. **The identity mapping of the kernel image covered only two megabytes**,
   and the kernel stopped booting as soon as it grew beyond that.
5. **The write in the serial console used a single buffer without
   protection**, and two tasks wrote over each other: the console reported
   lines that nobody had written. The write is now atomic.
6. **The latency of the delivery of a message used a constant**, and not the
   clock of the processor.
7. **The copy with overlapping ranges was checked only by its length**, and
   the arguments of the call were swapped in the user mode program. The test
   passed without proving anything. The verification now checks the content,
   byte by byte.
8. **The fourth argument of the call travelled in the fourth register**,
   which the `syscall` instruction replaces with the address of return. The
   value of the message reached the kernel as an address.

## 7. Security

### 7.1 Existing protections

- The bootloader validates the kernel image before executing it, and refuses
  any kind of relocation beyond `R_X86_64_RELATIVE`.
- The kernel validates the handoff contract, and refuses an unknown version
  instead of interpreting it by guesswork.
- Every range of memory that the kernel touches because of a call is checked
  in the page tables **of the space of the process that called**, before the
  access, and the check includes the user bit and the write bit.
- The processor frame of the way back is built in the kernel stack of the
  task, and never in a page of the user mode.
- Each process has its own address space, and the switch of the space
  follows the switch of the context.

### 7.2 Known limitations

- **There is no capability model.** A process reaches its whole address
  space, and the protection between processes comes from the structure of
  the tables, and not from a revocation.
- **The handling of exceptions is fatal.** An exception that comes from the
  user mode stops the machine, and not only the process.
- **There is no W^X nor NX by user control.** The kernel image is mapped
  with write, because the stack and the heap live in it.
- **There is no process recovery**, and neither the cancellation of a wait.
- **There is no resource protection** against a process that allocates
  without limit, because the allocation calls do not exist.
- **There is no validation on physical hardware.** All the validation is
  done in the emulator.

## 8. Build and tools

| Item | Version |
|---|---|
| Compiler | Zig 0.17.0 |
| Emulator | QEMU 10.2.2 (`qemu-10.2.2-1.fc44`) |
| Firmware | OVMF, from the `edk2` package of Fedora |

```bash
zig build                 # builds the boot image
zig build test            # unit tests on the host
zig build qemu-test       # boot test in QEMU with OVMF
zig build check           # unit tests and boot test
```

The firmware is looked for by the test script itself, which accepts the
`OVMF_CODE` and `OVMF_VARS` variables, the known paths of the distributions
and, as a last resort, a search of the file system. The firmware of four
megabytes is supported, and the format of each file comes from its name.

## 10. Continuous integration

The workflow is in
[`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) and runs on every
push and on every pull request to `main`:

1. Gets the code.
2. Installs Zig 0.17.0, and **checks** the installed version.
3. Installs OVMF and QEMU.
4. Lists the firmware files of the system, so that an environment failure is
   diagnosable.
5. Runs the unit tests.
6. Builds the artifacts.
7. Runs the boot test in QEMU.
8. Inspects the produced artifacts.

The result of the run that corresponds to the published commit is in the
release log. The constraint of the environment is the same of the local
validation: everything runs in the emulator, and not on physical hardware.

## 12. Downloads

The project offers **two** source packages, and they are not the same:

| Package | Origin | Content |
|---|---|---|
| `VorynOS-v0.1.0-dev.1-source.tar.gz` | Asset of this release, produced by `scripts/package-source.sh` | Filtered source code, without `internal/` and without administrative files |
| `Source code (zip)` and `Source code (tar.gz)` | Generated automatically by GitHub | The source code of the repository **without** the filtering of `export-ignore`, and therefore **with** the `internal/` folder |

**Use the official filtered package.** The automatic files of GitHub do not
respect the `export-ignore`, and the packaging script itself refuses to
publish a package that carries internal files.

The SHA-256 summary of the official package accompanies the file, and it is
reproducible: the script uses `gzip -n`, which does not write the
timestamps of the host, and the content comes from an immutable reference
of Git.

No disk image is published as an official artifact: the image is built by
the project itself, and the one that the boot test verifies is built in the
environment of the person who uses it.

## 13. Known limitations

| Subsystem | Limitation | Impact |
|---|---|---|
| Physical memory | Bitmap with coverage of up to 4 GiB | A machine with more memory uses only the first 4 GiB |
| Heap | Fixed region of 256 KiB inside the kernel image | The heap does not grow, and the memory of the heap is limited |
| Virtual memory | Only the kernel image and the framebuffer are identity mapped | There is no user space mapped by default, and the frame is the limit of 2 MiB |
| Processes | Two processes, and the limit of address spaces is a constant of the paging module | The number of processes does not grow with the demand |
| Thread | Does not exist: the task is the unit of execution | There is no parallelism inside a process |
| Syscalls | Eight calls, and the process has no allocation of its own | There is no memory allocation by the process, and neither files |
| IPC | The delivery and the wait exist; there is no ordering, guaranteed delivery, synchronization nor timeout of the wait | A process that waits depends on the other, and there is no way to give up |
| Capabilities | Not implemented | A process reaches its whole space |
| Exceptions | Fatal handling, without recovery | A failure in one process stops the machine |
| Storage | Without an operational file system in the kernel | There is no persistence |
| Drivers | Without general driver infrastructure | The hardware is accessed in a punctual way |
| Graphical interface | Not implemented | The serial console is the only channel |
| Physical hardware | Without documented validation | All the validation is done in the emulator |

## 14. Features that are still not implemented

The features below **do not** exist in this version, and they must not be
understood as delivered: threads and the life cycle of a thread; the
capability model of the VNC, with revocation; the memory allocation by the
process, and the dynamic heap with the VNM; the recovery of a process after
an exception, and the handling of exceptions by type; the timeout of the wait
and the wait for more than one channel; the file system, the block drivers
and the VNV; the graphical renderer and the desktop environment; the
network, audio and GPU drivers; the packaging of applications and the native
formats (VEX, VPK, VDRV, VCFG, VARC, VIMG).

## 16. Next priorities

1. **Handling of exceptions by type, with the recovery of the process.** It
   is the most visible gap of robustness: today an exception of a process
   stops the machine. The increment is small, and the design is already
   recorded in ADR-0006.
2. **Capability model of the VNC.** It is the most important gap of
   security, and the open question of ADR-0001 depends on it.
3. **Memory allocation by the process, and dynamic heap with the VNM.** The
   fixed heap of 256 KiB limits any program that is going to run.
4. **Timeout of the wait and wait for more than one channel**, which
   complete the IPC model.
5. **Threads**, with the thread life cycle and the scheduler per thread.
6. **Regression test for the exception path**, which today only has the
   coverage of the fatal report.
7. **Measurement of the cost of the context switch under a representative
   load**, with more tasks and more processes, and with the result in the
   performance report.

## 18. Versioning policy

The project follows the
[VVS-0001](../standards/VVS-0001.md), which defines the format
`MAJOR.MINOR.PATCH[-CHANNEL.N][+BUILD]`, the channels and the rules of
compatibility of the versioned contracts.

Section 8 of the VVS-0001 records the **extraordinary exception** that
authorized the republication of this same identifier: the earlier milestones
were experimental, their identifiers were discontinued, the source code was
not reverted, and the original commits remain preserved in the archive branch
`archive/versioning-reset-2026`. The exception does not establish a general
permission to reuse published versions.

The sequence from this milestone onwards is:

```text
v0.1.0-dev.1   ← this milestone
      |
      v
v0.1.0-dev.2   ← next verifiable increment
      |
      v
v0.1.0-dev.3
      |
      v
v0.1.0-alpha.1
```

## 19. Experimental notice

The VorynOS is in development. It is not recommended for production. There
is no validation on physical hardware. The interfaces of the kernel and the
system call contract may change. The features of section 14 remain
pending. What this version delivers is a consolidated and verified
foundation, and the base from which the rest of the operating system will be
built.

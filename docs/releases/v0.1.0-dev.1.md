# VorynOS v0.1.0-dev.1 — Notas de desenvolvimento

> **Estado:** notas preparatórias. A tag `v0.1.0-dev.1` e um GitHub Release
> não são criados por este documento. Este marco representa um snapshot de
> desenvolvimento, **não** um lançamento estável nem uma distribuição para
> usuários finais.

## Visão geral

O VorynOS é um projeto de sistema operacional independente, com código
próprio, desenvolvido prioritariamente em Zig 0.17.0 para x86_64 e firmware
UEFI. A arquitetura proposta é o **Voryn Fabric**. A base de código atual
abrange o carregador UEFI VNB, o núcleo VNK, contratos compartilhados,
infraestrutura inicial de execução e ferramentas de construção e teste.

Esta nota resume o estado documentado do projeto em
`docs/roadmap/phase-status.md`, incluindo o trabalho realizado antes das
tags `v0.1.0-dev.2` e `v0.1.0-dev.3`. Ela **não** afirma que esses
marcos foram recriados ou substituídos: as tags existentes continuam
independentes.

## Funcionalidades registradas no código e no roadmap

### Fundação e boot — F0 e F1

- Estrutura de build em `build.zig` e `build.zig.zon`, com ferramentas
  para gerar a aplicação UEFI, o kernel ELF64 e uma imagem EFI.
- Bootloader nativo UEFI com console, serial COM1, framebuffer GOP,
  descoberta do mapa de memória, carregamento ELF64 e contrato de handoff.
- Tratamento de `ExitBootServices` e transferência de controle para o
  ponto de entrada do kernel x86_64.
- Documentação arquitetural, ADRs, especificações, estratégia de testes e
  workflow de integração contínua.

### Kernel e memória — F2

- Entrada própria do kernel, GDT, TSS, IDT e tratamento de interrupções
  e exceções.
- Temporizador PIT, inicialização de memória física, tabelas de página
  próprias e heap inicial do kernel.
- Testes de inicialização e diagnóstico por console serial, conforme
  evidências históricas documentadas no roadmap.

### Execução e IPC — F3 (em desenvolvimento)

- Escalonamento preemptivo e troca de contexto entre tarefas do kernel.
- Execução inicial em modo de usuário (ring 3), caminho de syscall x86_64,
  verificação de endereços de usuário e contrato inicial de chamadas.
- Canal inicial VNX com troca de mensagens entre tarefa de usuário e
  núcleo. **Não** representa IPC entre processos independentes.
- As medições históricas do roadmap registram 358 ciclos no melhor caso
  para troca de contexto e aproximadamente 8 mil ciclos em média; esses
  valores não são benchmarks reproduzidos nesta preparação de release.

## Limitações conhecidas

- F3 ainda não está concluído: processos isolados e capacidades VNC
  permanecem propostos.
- O heap inicial é fixo em 256 KiB e o bitmap de memória física tem
  cobertura limitada a 4 GiB, segundo o roadmap.
- O tratamento de exceções ainda possui caminhos fatais.
- Não há validação documentada em hardware físico nesta preparação.
- Drivers de armazenamento, sistema de arquivos persistente, runtime de
  aplicações, interface gráfica, rede, áudio, compatibilidade e instalação
  para usuários finais permanecem em marcos futuros.
- **Não usar como sistema de produção nem para dados sensíveis.**

## Construção e testes

Os comandos documentados para um ambiente com Zig 0.17.0, QEMU e OVMF são:

```sh
zig version
zig build
zig build test
zig build qemu-test
zig build check
```

**Validação desta preparação:** revisão de arquivos e estado do repositório
remoto. **Não foram executados** compilação, testes de unidade, testes QEMU
ou testes em hardware durante a preparação destas notas. Os estados
“CONCLUÍDO” e “TESTADO LOCALMENTE” citados acima são os registrados no
roadmap, não uma certificação de uma nova execução de testes.

## Próximos marcos

1. Concluir F3 com processos, isolamento e IPC entre processos.
2. Estabilizar tratamento de erros e gerenciamento de memória.
3. Reexecutar CI, testes QEMU e validação de artefatos antes de publicar
   qualquer snapshot para download.
4. Evoluir progressivamente para F4 (armazenamento) e fases posteriores.

## Rastreabilidade e publicação

- **Versão pretendida:** `v0.1.0-dev.1`.
- **Canal:** `dev` — experimental, sem garantias de compatibilidade.
- **Referência pretendida:** o HEAD da branch `main` no instante de criação
  da tag; registrar o SHA exato quando a tag for efetivamente criada.
- **Situação:** documentação preparatória; não equivale a tag ou release.
- **Tags históricas existentes:** `v0.1.0-dev.2` e `v0.1.0-dev.3`.
- **Política:** `docs/standards/VVS-0001.md`. Uma tag `dev.1`
  publicada depois de `dev.2` e `dev.3` deve ser entendida como
  reorganização editorial retrospectiva, não como ordem cronológica.

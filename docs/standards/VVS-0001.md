# VVS-0001 — Voryn Versioning Specification

| Campo | Valor |
|-------|-------|
| **Estado** | ACEITO |
| **Data** | 2026-10-21 |
| **Escopo** | Todo o projeto VorynOS |

## 1. Objetivo

Definir uma política de versionamento única, previsível e auditável para o
VorynOS e para os contratos e formatos que exigem compatibilidade estável.

## 2. Formato

```text
MAJOR.MINOR.PATCH[-CHANNEL.N][+BUILD]
```

- `MAJOR`: mudança incompatível de contrato, formato ou arquitetura.
- `MINOR`: funcionalidade nova compatível com o contrato vigente.
- `PATCH`: correção de defeito sem alteração de contrato.
- `CHANNEL.N`: canal e contagem. Canais válidos, em ordem de estabilidade
  crescente: `dev`, `alpha`, `beta`, `rc`.
- `BUILD`: metadado de build, sufixo livre após `+`, para ferramenta
  automatizada (por exemplo `+20261021.3`). Não altera a ordem de
  precedência.

## 3. Canais

| Canal | Uso | Estabilidade |
|-------|-----|-------------|
| `dev` | Trabalho em andamento, sem garantia de contrato | Nenhuma |
| `alpha` | Funcionalidade incompleta, contrato instável | Baixa |
| `beta` | Funcionalidade completa, contrato congelado | Média |
| `rc` | Candidato a lançamento | Alta |
| (sem canal) | Lançamento | Máxima |

Regras:

1. A remoção do sufixo de canal é uma ação consciente, não automática.
2. `MAJOR.MINOR.PATCH` sem canal significa versão estável.
3. A parte `CHANNEL.N` reinicia a cada incremento de `MAJOR.MINOR`.
4. Sem canal, uma correção é um `PATCH`; com canal, é um incremento de `N`.

## 4. Compatibilidade de contrato

Contratos que exigem compatibilidade estável são versionados
**independentemente** da versão do sistema:

| Contrato | Versão própria | Onde vive |
|----------|----------------|-----------|
| Contrato de handoff VNB → VNK | `handoff_version` em `shared/handoff.zig` | `docs/specs/boot-handoff-spec.md` |
| Formato VEX | `VEX` | `docs/specs/` (planejado) |
| Formato VPK | `VPK` | `docs/specs/` (planejado) |
| ABI de syscall | `syscall_abi` | planejado para F3 |

Regras de compatibilidade:

1. Um campo nunca é removido de um contrato versionado; ele é reservado.
2. Novos campos são adicionados ao final da estrutura e o `header_size` ou o
   tamanho de entrada é incrementado.
3. O consumidor **precisa** rejeitar uma versão desconhecida, em vez de
   interpretá-la por adivinhação. O contrato de handoff já faz isso: magic e
   versão são verificados antes de qualquer uso.
4. A mudança de layout de um contrato exige `MAJOR` do sistema ou uma versão
   maior do próprio contrato, com prova de que as duas partes concordam.

## 5. Estados e versão

- Uma funcionalidade que ainda não existe **não** recebe versão de
  lançamento.
- A versão do sistema descreve o **estado do código**, não a intenção.
- O número de versão de uma marco (F0, F1) é registrado em
  `docs/roadmap/phase-status.md` junto ao estado real.

## 6. Formatos nativos

Cada formato nativo (`.vex`, `.vlb`, `.vpk`, `.vdrv`, `.vcfg`, `.varc`,
`.vimg`) carrega, no seu cabeçalho:

- `magic` de 8 bytes;
- `format_version` de 16 bits, independente da versão do sistema;
- `header_size` de 16 bits;
- `flags` de 32 bits, com o bit superior reservado para "extensão
  obrigatória" (um leitor que não conheça a extensão deve recusar o
  arquivo).

## 7. Proibições

1. Não publicar tag ou release sem autorização explícita.
2. Não reutilizar um número de versão já publicado.
3. Não atribuir `MAJOR` maior que o necessário: a versão major é reservada
   para quebra real de contrato.
4. Não declarar um recurso como "estável" enquanto ele não for exercitado
   pelo teste automatizado correspondente.
